# PMM4RPAAI-Sim — project memory for Claude

> Process Mining + Modeling for RPA/AI Simulation.
> Determine, via simulation, whether automating an activity in a discovered
> business process will meet stakeholder goals (cycle time, cost, …) under
> a Taguchi design-of-experiments.

This file is the canonical orientation for anyone (or anyone's Claude) joining
the project. Read it before editing.

---

## 1. What the tool does

```
Event log (XES/CSV)
        │
        ▼  Simod  (one-shot, Java 8 + SplitMiner)
BPMN model + Prosimos simulation-parameters JSON
        │
        ▼  user picks: target activity  (pattern fixed: XORSplitAutomation)
Pattern.parameters(target) → N factors × 3 levels (Taguchi)
        │
        ▼  curated L9 and L18 OAs
list[Scenario]  (one per row of the OA)
        │
        ▼  Pattern.apply(scenario)  — mutates BPMN + JSON
        │
        ▼  Prosimos  start-simulation  ×  N replications
Per-replication event-log CSV + stats CSV
        │
        ▼  pandas-derived metrics  +  Taguchi S/N + ranking
Ranking table + main-effects view + export (Statistics CSV, S/N CSV, Params ZIP, BPMN, Event logs ZIP, Model ZIP)
```

## 2. Architecture seams

**`XORSplitAutomation` is the only substitution pattern and no second pattern will be added** — it is central to the client's thesis. The `Transformation` ABC and `REGISTRY` exist for clean encapsulation, not extensibility. The UI reflects this: Panel 1 renders **no pattern picker** — it shows the pattern name read-only (`st.caption`) and `app.py` binds the sole `REGISTRY` entry via `next(iter(REGISTRY.values()))`, never naming the concrete class. The abstraction is retained regardless; re-add a `st.selectbox` there if a second pattern ever appears (it won't). Three contracts define that boundary:

- **`Transformation`** ([core/transformations.py](core/transformations.py)) — abstract base declaring the pattern's contract (the abstract methods listed below), plus a concrete `prepare_experiment()` that coordinates them (`apply_pattern()`, the `verify_transformed()` gate, then `build_scenario_template()`):
  - `parameters(current_duration_s, selected_pool_size, frozen_pool_size) → list[Parameter]`
    declares the factors the pattern exposes. The UI auto-renders them; the
    Taguchi designer auto-fits an OA. Deliberately takes no target activity —
    factor declaration depends on the target only through the discovered
    context the caller resolves (duration, pool sizes), unlike the other
    contract methods, which locate the task in the BPMN and so do take it. `selected_pool_size` is the discovered
    human pool size the `num_manual_resources` levels centre on (`_manual_pool_levels`).
  - `prepare_experiment(bpmn_in, json_in, target, out_dir, ...) → BpmnTransformResult`
    is **concrete** — once per experiment it calls `apply_pattern()`, gates on
    `verify_transformed()` (ERROR-tier violations write `out_dir/validation.log`
    via `store.validation_report` and raise `TransformValidationError` with the
    report's content as its `log_tail`, the mis-wired model kept on disk beside
    the report for inspection; WARNINGs log without raising), then calls
    `build_scenario_template()` and packs the results into a
    `BpmnTransformResult` carrying `bpmn_path`, `scenario_template`, `ids`, and
    `selected_resource_id`.
  - `apply_pattern(bpmn_in, target, out_dir) → (Path, TransformIds)` mutates the
    BPMN once (adds the pattern's gateways/task/flows) and writes it out.
  - `verify_transformed(bpmn_path, target) → VerificationResult` structurally
    verifies the pattern's fragment in a transformed BPMN (XOR impl: a
    one-liner over `bpmn/validate.verify_fragment`). Abstract so the
    pattern-agnostic ABC never names a concrete verifier; `transformations.py`
    also owns `TransformValidationError` (report path + `log_tail`, the
    run-failure surface's `SimulationError.log_tail` contract), which the
    gate raises.
  - `build_scenario_template(json_in, ids, bot_cost_per_hour) → dict` loads the
    Prosimos JSON and injects the pattern's shared infrastructure — the
    scenario-template each scenario deep-copies.
  - `params_from_values(values, result) → ScenarioParams` converts one Taguchi
    row into the pattern's typed params object. Keeps `orchestrator.py` free of
    any concrete subclass imports.
  - `baseline_params(result) → ScenarioParams` returns the no-intervention
    baseline params (the pattern applied with 0% automation, Simod-discovered
    durations/staffing). Keeps `orchestrator.py` pattern-agnostic — it never
    constructs `pct_auto=0` itself.
  - `apply_params(template, ids, params, out) → Path` deep-copies the template
    and injects scenario-specific values. Called once per scenario.
  - The only pattern: `XORSplitAutomation` — the 4-gateway / 2-activity
    pattern in §4.

- **`Parameter`** ([core/parameters.py](core/parameters.py)) — `{id, label,
  levels:[3], kind}`. `kind` (`"percentage"`, `"duration_s"`, `"categorical"`,
  `"cost"`) drives `number_input` constraints in the UI via `number_input_kwargs()`
  in `ui/param_inputs.py` (min/max/step/format). The pattern reads `values` by
  id directly and does not use `kind`.

- **Job-folder store** ([core/simulation/store.py](core/simulation/store.py)) — every experiment
  is a folder under `runs/<exp-id>/`. Replications land at
  `runs/<exp-id>/scenarios/<sid>/rep_NNN_log.csv` + `..._stats.csv`. Tidy
  long-format DataFrame in `app.py` is the single source of truth for
  analysis — keeps re-ranking decoupled from re-simulating.

| [core/simulation/executor.py](core/simulation/executor.py) | Parallel simulation executor. `SimulationTask` dataclass: `bpmn_path`, `json_path`, `n_cases`, `out_log`, `out_stat`, `proc_log`, `metadata`, `max_retries`. `run_all(tasks, on_complete, on_error=None, max_workers=None, stop_check=None)` runs all tasks in a `ThreadPoolExecutor` (`max_workers` defaults to `os.cpu_count()`), retrying each up to `task.max_retries` times before calling `on_error`. `on_complete` and `on_error` are always called on the calling thread via `wait()`, so callers can safely mutate shared state without locks — the one exception is the internal `_LiveProcesses` registry (lock-guarded, worker-thread-written; holds each running `Popen` via `on_spawn`). `stop_check` is a zero-argument predicate polled every `_STOP_POLL_SECONDS` (0.5s) via a timeout `wait` — not just after each completion, so a cancel is seen even while every worker is mid-replication; on cancel `_LiveProcesses.kill_all()` terminates the in-flight subprocesses in parallel so the pool join unblocks promptly. | [core/simulation/prosimos/replication_metrics.py](core/simulation/prosimos/replication_metrics.py) | Per-replication metrics from Prosimos output — its centre of gravity is derivation, not parsing: every product metric comes from the **event log + params JSON**; the stats CSV is not a product source. `replication_metrics(log_csv, params_json, bot_task_name, original_task_name)` returns a `ReplicationMetrics` frozen dataclass (`mean_cycle_h`, `median_cycle_h`, `min_cycle_h`, `max_cycle_h`, `mean_cost`, `total_cycle_s`, `total_cost`, rework fields, `total_bot_failure_count` — matching the `COL_*` constants via `dataclasses.asdict()`). Logs are activity-only (the runner omits `--is_event_added_to_log`): a row with `resource == NO_RESOURCE` (`"No assigned resource"`, Prosimos's intermediate-event marker) means the log came from a flag-on run, and `replication_metrics()` raises a `ValueError` naming the flag rather than parsing it (looped timer rows would count as rework, zero-length event spans would drag `min_cycle_h`). ## 4. The current substitution pattern (`XORSplitAutomation`)

For a target activity *Act*, the pattern produces this fragment:

```
  ─►(XOR1)──%Auto──►[Auto Act]──►(XOR2)──%OK──────────────────►(XOR4)─►
        │                              │
      100-Auto                      100-OK
        │                              │
        └──────────►(XOR3)◄────────────┘
                      │
                      ▼
                    [Act] (the original, non-automated path) ──►(XOR4)
```

**Six factors** (`parameters()` declares them; UI auto-renders). Six factors → L18 OA → 18 scenarios (5 when the manual pool is frozen — still L18; `pick_array`'s L9 cut is ≤4 factors). Cases per replication is **not** a factor: it is a run-config scalar beside `n_reps` (client decision 2026-07 — simulation scale, not a process-design factor; see the §8 per-case-vs-aggregate bullet for what its removal changed).

| Factor | Default levels | Meaning |
|---|---|---|
| `pct_auto` (%) | 25 / 50 / 75 | XOR1 branch probability to the automated task |
| `pct_ok` (%) | 80 / 90 / 95 | XOR2 success probability (skip the fallback) |
| `t_auto` (s) | 5%, 10%, 20% of Simod mean | Automated task mean duration |
| `t_manual` (s) | 80%, 100%, 120% of Simod mean | Non-automated mean (**prepopulated from Simod**) |
| `num_bots` | 1 / 2 / 3 | Bot resource pool size (a *new* pool — not discovered-centred) |
| `num_manual_resources` | discovered pool *n* ±1 → `[n-1, n, n+1]` (floor: *n*=1 → `1/2/3`) | Human resource pool size, centred on the Simod-discovered pool (`_manual_pool_levels`) |

`apply_pattern()` (BPMN) and `build_scenario_template()` + `apply_params()` (JSON) do:
- **BPMN**: rewires the target task's incoming → XOR1 and outgoing ← XOR4;
  adds 4 exclusive gateways, 1 task (`"Auto " + original name`), and 7 new
  `<sequenceFlow>` elements. Uses `xml.etree.ElementTree`; preserves the default BPMN namespace.
- **JSON**: keeps the original task's `task_resource_distribution` entry but
  replaces its duration with a small-jitter uniform around `t_manual`. Clones
  the resources list into a second entry for the new `Auto` task with
  uniform around `t_auto`. Appends **four** entries to
  `gateway_branching_probabilities`: XOR1 (split) and XOR2 (split) carry
  scenario-specific probabilities; XOR3 and XOR4 (merges) always carry
  `value: 1.0`. **All four are required** — Prosimos validates that every
  gateway has an explicit probability entry and will reject the params JSON
  if any are missing, even for single-path merges.

**Known limitation:** only single-entry/single-exit tasks (exactly one incoming +
one outgoing sequenceFlow) are supported. A task with multiple incoming or outgoing
flows is a spec-legal *uncontrolled* merge/split — **not** a malformed model, and
**not** the same as a gateway-fed task (a task fed by a gateway has arity 1 and
transforms fine); its canonical form routes the branching through an explicit
gateway, leaving the task 1-in/1-out. `apply_pattern()` raises `NotImplementedError`
on the uncontrolled shape rather than producing a broken model. It does not arise in
practice: the pipeline input is always an event *log* and SplitMiner emits the
explicit-gateway (canonical) form, so a discovered task is 1-in/1-out. The guard is a
defensive backstop for input that isn't — an assumption about the miner we do not
fully verify — failing loud rather than corrupt.

**Multi-resource design decision:** a target activity may have multiple resources
assigned, but they are always of the same type (all human OR all bot — never mixed).
Rather than scaling all resources together, the UI lets the user pick which single
resource's pool to vary via the `num_manual_resources` factor. Shared resources
(assigned to more than one task) are shown but disabled in the selector — changing
their pool size would affect other tasks and is considered out of scope. The
factor's three levels are **centred on the selected resource's Simod-discovered
pool size** `n` → `[n-1, n, n+1]` (floored to `[1, 2, 3]` when `n=1`) via
`_manual_pool_levels()`, mirroring how `t_manual` centres on the discovered mean;
`num_bots`, a *new* pool, stays a fixed `[1, 2, 3]`. `DEFAULT_MANUAL_POOL_SIZE=1`
is the fallback when no pool size is known (demo / pre-discovery). A selected
resource that resolves to no profile is a malformed model — surfaced loudly via
`_halt_if_unresolved()` in `ui/interactive/resource_selector.py`, never a silent
fallback. If all
resources on the task are shared, `num_manual_resources` is frozen at its current
Prosimos value and excluded from the Taguchi OA. The selected resource ID is passed to `prepare_experiment()`, carried through
`BpmnTransformResult.selected_resource_id`, and forwarded to
`AutomationParams.selected_resource_id` via `params_from_values()`.
`None` means skip the pool resize (leave the human resource pool unchanged).

## 5. Hard-won setup caveats (Windows)

Captured from the bootstrap session — flag these in any new install guide.

1. **Simod requires Python 3.9 + Java 8.**
   - `winget install Python.Python.3.9 --source winget` (the msstore source
     fails certificate verification — `--source winget` is mandatory).
   - `winget install Amazon.Corretto.8.JDK --source winget`.
   - Do **not** set system `JAVA_HOME` to Corretto 8 — the runner injects it
     only into Simod's subprocess via the `JAVA_HOME` override field. Other
     tools on this machine still use the system Java.

2. **TLS-inspecting middlebox.** Fresh Python 3.9 `pip` fails SSL verify
   even after upgrading certifi. The fix: a `pip.ini` in each venv root
   (`tools\simod-venv\`, `tools\prosimos-venv\`) pinning
   `trusted-host = pypi.org files.pythonhosted.org pypi.python.org` — the
   venvs are gitignored, so it must be recreated per clone. Without it,
   `pip install simod` will hang on retries forever.

3. **Prosimos needs a tz-aware `--starting_at`.** Passing
   `"2025-01-01T00:00:00"` (naive) crashes inside
   `simulation_stats_calculator.py` comparing naive vs aware datetimes. The
   runner now defaults to `"2025-01-01T00:00:00+00:00"`. Don't drop the
   offset.

4. **Simod accepts CSV only.** XES inputs are converted by
   `runner.xes_to_simod_csv()` using stdlib `xml.etree.ElementTree` (XES is
   well-specified XML; no pm4py needed). The XES from pm4py-ucm has only
   `complete` events, so `start_time` is synthesized per case from the
   previous event's `end_time` (zero-duration for the first event). The
   parser expects namespace `http://www.xes-standard.org/` and raises a clear
   `ValueError` for empty logs or events missing `time:timestamp`.

## 6. The Streamlit rerun trap (the bug that bit us twice)

Streamlit re-runs the whole script top-to-bottom on **every widget
interaction**, even while a long synchronous subprocess is mid-flight.

In our first guard, the upload fingerprint was set *after*
`runner.discover()` returned. During the 2-minute Simod run, any browser
refresh restarted the script, saw `log_fingerprint == None`, and kicked off
another concurrent Simod. We caught one occurrence at **six** concurrent
Simod processes started inside seven seconds.

The guard against concurrent discovery (in [app.py](app.py)): real discovery now
runs in a **background thread** (`ui/services/discovery_manager`), so a second one can't
start while one is in flight — the sidebar routes on `discovery_phase(ss,
upload_fp)`, whose `RUNNING` case `st.stop()`s before `needs_discovery` is even
reached, and the upload fingerprint stops the same file re-triggering. (Before
the background-thread move this was a synchronous `ss.discovering` boolean
claimed *before* the subprocess call with a `finally` release — the interrupt
corollary below is the story of why that approach was fragile and got replaced.)

**Rule for the codebase: blocking work triggered by a widget belongs in a
background thread — `run_manager` for experiments, `discovery_manager` for
discovery — polled by an `@st.fragment`, never a synchronous call in the main
script thread, which `fastReruns` can interrupt mid-flight.**

**The interrupt corollary (two bugs one gesture — a stranded lock AND a stale
guard).** Uploading a log and then nudging a run-config widget before the
sidebar "blurs" (the pre-`st.status` window, widened by the multi-MB
`write_bytes(uploaded.getbuffer())`) makes discovery hang until the user clicks
Cancel. Two distinct causes, both rooted in how `runner.fastReruns` (Streamlit's
default) handles a rerun requested mid-run: `AppSession` calls `request_stop()`
on the running ScriptRunner **and immediately spins up a new ScriptRunner on a
fresh thread** — it does *not* wait for the old one to stop. So the guard runs
**concurrently** with the still-running discovery thread. (1) *Stranded-lock
half:* the running discovery thread is stopped at its next yield point (every
`st.*` call is one; `request_stop` surfaces as a `BaseException` that
`except Exception` does not catch). The lock claim and the `try/finally` that
releases it must therefore be **adjacent** — claim `ss.discovering = True`, then
open the `try` on the very next line. The original block opened its `try` far
down at `st.status` with the release scattered across four manual
`ss.discovering = False` lines, so a stop between claim and `st.status` stranded
`discovering=True`. Fix: one `try` immediately after the two-line claim, one
`finally: ss.discovering = False`, four scattered releases deleted.
**The fix — discovery runs in a background thread (like simulations).** The
synchronous version was fundamentally fragile: a heavy blocking call in the main
script thread is at the mercy of `fastReruns` spawning a competing thread on any
interaction. The durable fix moves real discovery off-thread, mirroring the
simulation-execution pattern: `ui/services/discovery_manager.py` (Streamlit-free, the
discovery counterpart to `run_manager`) runs `runner.discover` in a daemon
thread and exposes `start_discovery`/`discovery_phase`/`commit_discovery`/
`clear_discovery` + `DiscoverySession`/`DiscoveryResult`/`DiscoveryOutcome`;
`ui/interactive/discovery_panel.py` is an `@st.fragment` that polls the
`DiscoverySession` while it runs. A run-config nudge during discovery now just triggers a full rerun that
re-renders the progress fragment — the background thread is untouched, so Simod
is never interrupted. Polling uses **`@st.fragment(run_every=...)`**, whose
timer auto-reruns are fragment-scoped (only the panel re-renders → no full-page
flicker); on completion the fragment commits the result and does one
`st.rerun(scope="app")` for a full re-render. A first attempt polled with a bare
`st.rerun()` and **flickered anyway** — `st.rerun()` defaults to `scope="app"`,
so it was doing a full-page rerun every tick (the stop-icon/tab-title flicker),
and that rerun storm also swallowed the Cancel click; `scope="fragment"` is not
an option (it raises on the fragment's first full-run invocation), so `run_every`
is the idiomatic fix. The lifecycle (running / failed / cancelled / done / idle)
is an **explicit state machine keyed by the upload fingerprint** — see the
discovery-state-machine bullet in §8 for why the earlier ad-hoc flags
(`current_discovery` + a separate `discovery_settled` + `log_fingerprint`)
drifted and let a settled banner persist across a log change. This retires the whole
`discovering` boolean lock and its guard: `discovery_phase(ss, upload_fp)` is
the single router, and because the work is off-thread the pre-`st.status`
abort window (the stranded-lock half above) no longer exists in the main thread.
A `time.sleep(0.5)` + `st.rerun()` poll on the *old synchronous guard* was tried
first and **reverted** — a full-page (not fragment-scoped) rerun flickered the
whole page, and it flickered for the entire ~2 min when the nudge landed during
Simod. Demo discovery stays synchronous (pre-baked model, no subprocess, instant).

**Second Streamlit trap — `value=` is only the *initial* value.** Once a widget
key exists in `session_state`, `st.number_input(..., value=X, key=K)` ignores
`X` on every later rerun and shows the stored value. This silently broke the
factor-level inputs: switching the target activity recomputes `current_dur` (so
the t_manual levels and the caption update), but inputs keyed by a stable
`f"{p.id}_{i}"` stayed pinned to the old target's numbers — and
`p.levels = new` then fed the *stale* values into `build_scenarios`. Fix (now in
[ui/interactive/factor_levels.py](ui/interactive/factor_levels.py)): include the computed default in the key —
`key=f"{p.id}_{i}_{p.levels[i]}"` — so a widget re-defaults exactly when its
level changes (target → new `t_manual`, resource → new `num_manual`), while
fixed factors keep a constant key and preserve user edits across a target switch.

## 8. What's worth doing next

Known bugs / reliability gaps:

- **Incomplete cases in cycle time** (`core/simulation/prosimos/replication_metrics.py`): `replication_metrics()`
  computes every metric from the event log now, so the old cross-source contamination
  objection is gone — a completion filter (dropping cases with any NaT `end_time`) would be a
  clean one-liner over one DataFrame, no stats-CSV total to poison. It is deliberately **not**
  applied: Prosimos runs until `--total_cases N` cases **complete** and writes all three
  datetimes on every task row, so a filter would be dead code that would *mask* a Prosimos bug
  if truncation ever appeared (a NaT would instead propagate to a loud NaN mean). Only revisit
  if that guarantee changes.

Design decisions:

- **DI-less BPMN is rejected at the boundary; the adders take a resolved `plane`**
  (`core/transformations.py`, `core/bpmn/edit.py`): a BPMN with no `<BPMNDiagram>` is
  schema-legal (DI is `minOccurs="0"`) and Prosimos-executable (it routes off
  `sourceRef`/`targetRef`), so the model is not *invalid* — but `apply_pattern` now raises
  `ValueError` on one rather than transforming it. Two reasons: the BPMN is an
  **externally-inspected export** (Panel 5's "BPMN" button) and diagram-first tools
  (bpmn.io, Camunda Modeler, Apromore) cannot render a DI-less model, so it misses the
  verifiability bar; and we cannot cheaply *repair* one, since this module pushes layout to
  callers via `_xor_bypass_layout`. **This fixed a real corruption bug**, not a
  hypothetical: the three adders each opened with `plane = get_plane(root)` /
  `if plane is None: return`, so on a DI-less model they added **nothing** while
  `update_flow_target` did its process work regardless — retargeting the *real* flows at
  gateways that were never created. The output was a **silently broken model, not an
  untouched one** (measured: 2 dangling `targetRef`s, 3 `verify_fragment` ERRORs).
  Unreachable in production (the BPMN is always a Simod discovery, and Simod always emits a
  diagram), but it corrupted from otherwise-valid input, which was the defect.
  Three decisions encode the fix. (1) **Validate once, at the trust boundary.** The plane is
  resolved in `apply_pattern` beside its three existing preconditions (no `<process>`,
  activity not found, flow arity) — `edit.py` is *internally* public (only
  `transformations.py` imports it), so it does not re-check an external precondition its one
  caller already settled. (2) **Encode the assumption in the type, don't re-validate**
  ("parse, don't validate"): the adders take a non-optional `plane: ET.Element`, so mypy
  guarantees non-None at every call site and the DI-less case is *unconstructible* rather
  than guarded — which is why the three `test_no_op_when_no_plane` tests were deleted, not
  rewritten. **`root` is gone from `edit.py` entirely** — every mutator now takes
  `(process, plane, …)`. The adders only ever used `root` to find the plane;
  `add_flow_el` needed it one more level down, for `_waypoints_between` →
  `get_shape_bounds(root, …)`, so `query.get_shape_bounds` was reshaped to take the
  **plane** (its only caller). That cascade is what completes the convention rather
  than half-applying it: `_redraw_edge` was already resolving the plane and throwing
  it away, so it takes one now too, and `update_flow_target` loses `root` with it —
  and `edit.py` no longer imports `get_plane` at all. `diagram_extents(root)` is
  deliberately **not** pulled in: it is `transformations.py`'s layout helper, not
  `edit.py`'s, and it has tests pinning its no-diagram default.
  (3) **`if plane is None: return` is the one shape every convention rejects** — it neither
  trusts nor fails, it *hides*. Note `_redraw_edge` keeps a `plane is None` guard and that is
  **not** the same shape: DI work is *all* it does, so returning early is a genuine no-op
  rather than a skipped side-effect. `update_flow_target` likewise still accepts a DI-less
  model — its process work is real and only the redraw needs a diagram (this is the
  ref-list-maintenance rule: the lists, and the `sequenceFlow` itself, are process-level
  truth, not DI decoration). **The trap, if this is ever revisited: all three adders move
  together.** `apply_pattern` calls `add_task_el` → `add_xor_el` ×4 → `update_flow_target`
  ×2 → `add_flow_el` ×7, so fixing only `add_flow_el` would create 7 flows pointing at
  gateways its still-bailing siblings never made — taking 2 dangling refs to ~9, strictly
  worse than the bug. The alternative considered and rejected was TOLERATE (adders do
  process work unconditionally, guard only the `add_shape`/`_add_edge` calls locally): it
  would keep `_xor_bypass_layout` computing coordinates from `diagram_extents` on an empty
  plane for shapes that are then never written, to produce a model the product cannot render.
- **`add_flow_el` asserts its endpoints are flow nodes** (`core/bpmn/edit.py`): the latent
  twin of the DI bug on the referential axis — `add_flow_el` set `sourceRef`/`targetRef`
  unconditionally, then called `_link_flow_refs`, which **silently skipped** a missing node,
  yielding a dangling flow with no error. It now asserts both endpoints resolve *before*
  building the element (so a rejected call leaves no half-wired `sequenceFlow`), making the
  dangling-flow class unconstructible in `edit.py`. `assert`, not `raise`: this is caller
  misuse, not bad external input — in `apply_pattern` every node is added before any flow
  references it (the exceptions-at-boundaries / assertions-internally split, matching the
  existing production asserts in `orchestrator.py`/`transformations.py`). That split is why
  `apply_pattern` also rejects an outgoing flow with **no `targetRef`** itself: the pattern
  reuses the target's exit arc, so `outgoing[0].get("targetRef", "")` would otherwise hand
  `""` down and trip the assert — an internal caller-bug signal — on what is really
  malformed *input*. Bad input is the boundary's to reject; the assert only ever fires on a
  wiring mistake.
  **`_find_node_by_id` excludes `sequenceFlow`** — the assert is only as strong as the
  lookup, and matching *any* element by id let a flow id through, producing exactly the
  dangling ref the assert exists to stop (plus an `<incoming>` parented on a
  `<sequenceFlow>`, which `tSequenceFlow` does not permit). Flows and nodes share one id
  namespace and `apply_pattern` juggles both (`in_flow_id`/`out_flow_id` sit beside the
  gateway ids), so a flow-for-node slip is *the* realistic caller error — the one case a
  weaker check would miss. Excluded rather than whitelisting flow-node tags: a whitelist
  would have to enumerate every task/gateway/event subtype (`BPMN_TASK_TAGS` covers only
  tasks) and would reject **valid** models on any subtype it missed — worse than the
  weakness it fixes. A blacklist can only ever reject what is definitely not a flow node.
  **`update_flow_target` asserts its `new_target` too**, so both entry points to the
  dangling-ref class are closed rather than one. It is the *caller-supplied* target that
  is asserted — **not** `src`, which is read off the flow in the model and stays
  tolerantly skipped by `_link_flow_refs`, because a sourceRef pointing nowhere is
  malformed input, not caller error. Unguarded, a bad target landed *worse than a no-op*:
  `_unlink_incoming` dropped the old target's `<incoming>` and nothing replaced it. No
  live defect drove this (in `apply_pattern` the target is always a gateway created
  moments earlier) — it completes the invariant and removes an asymmetry a reader would
  otherwise have to explain away.
  **The assert lives in `add_flow_el`, not in `_link_flow_refs`**, even though the silent
  skip is in the latter: `_link_flow_refs` is *also* called by `update_flow_target`, which
  legitimately tolerates a target that isn't a process node, so hoisting the assert down
  into the shared helper would impose `add_flow_el`'s stricter contract on a caller that
  doesn't hold it. The dangling-flow path therefore remains constructible via
  `update_flow_target` — deliberate, since `apply_pattern` only ever retargets onto gateways
  it just created; if that ever stops being true, the assert belongs there too.
  Note `_link_flow_refs` looks up **process nodes** while `_waypoints_between` looks up **DI
  shapes** — different lookups, so the waypoint fallback is *not* dead code under this
  assert: a node can legitimately exist in the process while the diagram never drew it
  (`_BPMN_XML_UNDRAWN_NODES` in `tests/bpmn/test_edit.py` is exactly that case).

- **Per-case vs aggregate ranking** (`core/analysis.py`, `app.py`): `rank()` uses per-case metrics (`COL_MEAN_CYCLE_H_MEAN`, `COL_MEAN_COST_MEAN`, `COL_REWORK_RATE_MEAN`) rather than aggregate totals. Since cases-per-replication became a run-config scalar (client decision 2026-07), every scenario runs at the same scale, so `total = per_case × n` with one shared `n` and **per-case and totals ranking produce the same ordering** — the historical objection to totals (a `num_cases=1000` scenario out-totalling a more-efficient `num_cases=100` one purely on scale) no longer applies. Per-case stays the ranked representation because it is the honest per-unit efficiency number and keeps `rank()`/`Goal` thresholds independent of the run-config value; the client confirmed (2026-07) keeping per-case in the ranked table, with totals possibly displayed for a future use — now a pure presentation choice with no correctness stake. Aggregate columns ("Total Cycle Time (h)", "Total Cost ($)") remain excluded from Panel 5's ranked table and live in the Baseline tab's comparison view, where all scenarios compare against the single baseline at the run's case count.
- **Piecewise-linear goal satisfaction scoring** (`core/analysis.py`, `core/goals.py`, `app.py`): `rank(agg, goals)` accepts up to three `MetricGoal` objects (one per active metric) and scores each scenario on every metric goal independently. Each indicator scores on a piecewise-linear scale [0, 100]: 100 when it hits or beats the target, 50 at the baseline value, 0 at the worst-case breakpoint, interpolated linearly between these anchors; a metric goal's score is the weight-normalised mean of its selected indicators' scores. The aggregate `score = min` of all per-metric scores (weakest-link — the scenario is only as good as its worst-performing metric). The indicator weights are strictly intra-metric; there are no *cross-goal* weights (see the indicator-model bullet below). `rank()` emits a `{column}_score` column (float, rounded to 1 dp) per metric goal, plus aggregate `"score"`. Sort order is descending `score`. Breakpoints are **user-editable absolute values** (client requirement 2026-07): `ui/interactive/goal_config.py` renders Target/Worst inputs per selected indicator, defaulted via `Goal.from_indicator(indicator, baseline)` — the factory reads the indicator's mean column and direction and computes breakpoints via `Goal.from_baseline()` using `±GOAL_IMPROVEMENT_PCT` (10%) around the baseline; `baseline_ref` stays pinned to the measured baseline (a fact, not a knob — shown read-only). `GOAL_IMPROVEMENT_PCT: int = 10` is exported from `goals.py` so the UI caption stays in sync. `baseline_per_case()` in `core/goals.py` picks the per-case values out of the orchestrator's flat `baseline_agg` record (per-case means are stored at source, never derived by dividing totals); `demo.demo_baseline_agg()` returns the same flat shape, and `app.py` owns the single resolution site (real → `baseline_per_case(ss.baseline_agg)`; demo → demo constants; real with no baseline → `None`, which hides the threshold inputs and — when results exist — triggers the Panel 5 baseline-failed `st.error`). Goals render inside Panel 3, which sits behind the `ss.log` gate, so no pre-gate defensive init is needed.
- **Per-metric weighted indicator model** (`core/metrics.py`, `core/goals.py`, `core/analysis.py`, `core/simulation/prosimos/replication_metrics.py`, `ui/interactive/goal_config.py`, `ui/table.py`): a metric (cost / time / rework) scores on one or more **indicators** — per-case contributing factors, each judged against its own Target/Worst thresholds. `Metric.indicators: tuple[IndicatorSpec, ...]` holds them (`[0]` the locked default, the rest user-selectable extras); a `MetricGoal` bundles one `Goal` per selected indicator plus positive float weights (sum-normalised, so only ratios matter — floats buy typing `0.7/0.3` directly, not expressive power) and scores them as a weight-normalised mean. This generalizes the earlier hardcoded two-factor time goal (mean+median behind a 0–1 slider): `CYCLE_TIME` now offers mean / median / min / max cycle time, `REWORK_RATE` offers rework rate + mean rework count per case, `COST` stays single-indicator. Two load-bearing invariants: (1) the cross-metric aggregate stays weakest-link `min` — the indicator weights are strictly *intra-metric*, never a cross-goal weight; (2) the extra per-case indicators (median/min/max cycle, mean rework count) are **scoring-only** and NEVER enter the `total_cycle_s = mean × n × 3600` identity — the mean carries the totals, which is why the ranked and S/N metric stays the default indicator. **Adding an indicator is a ~4-file change** — a `COL_*` pair in `constants.py`, an `IndicatorSpec` in the registry, a `ReplicationMetrics` field + computation in `replication_metrics.py`, and the demo formula/baseline in `demo.py`; everything downstream (`aggregate()`, `_NON_FACTOR_COLS`, `baseline_per_case()`, the orchestrator's `baseline_agg` per-case half, the goal-config multiselect, the ranked-table columns) is **registry-driven** and needs no edit. `TestRegistryReaderCoherence` (`tests/test_metrics.py`) is the loud seam standing in for a data-driven reader: it fails if a registry `results_column` isn't a `ReplicationMetrics` field or if `mean.column != results_column + "_mean"`. Rejected alternatives: a **file-per-indicator package** (`metrics/cost/max.py`) — the computations share one reader pass, the definitions are tiny data, and the set is closed, so the registry tuple is strictly cheaper; a **data-driven reader** — the indicators derive from two different source series (`cycle_h`, `rework_per_case`), so registry-driving it would couple layers for ~3 lines of pandas (the coherence test buys the loudness without the coupling); `Goal`-as-the-container — it would churn ~35 passing breakpoint/score tests to relabel a concept, so `MetricGoal` is a separate container and `Goal` stays the single-indicator unit (its identifying field is `indicator_column`, not `metric`, since a `Goal` scores one indicator and letting both class levels say "metric" collapsed the distinction). **Cost extras** were once the one expensive case, but the first-principles migration (see the "First-principles metrics + trust checker" bullet) built the per-case cost series (`calendars.event_costs` → per-case sum; `mean_cost` is its mean), so cost min/max/median indicators are now the same ~4-file recipe as any other — a deferred follow-up, no longer blocked. `selected_extras`, the overrides, and the selection dict are all keyed by **column string** (not `Metric` object), so the `st.selectbox` value-copy `==`/`is` trap — the reason the old `second_factor` had to match by value — is structurally unreachable. **Panel 3 layout**: the goals render in a full-width `app.py` container as **one `st.tabs` tab per goal slot** — each goal's grid gets the whole page width, and only the active tab's grid contributes height, so the panel stays short at any goal count; the weight input is a fifth grid column beside Target/Baseline/Worst (omitted when only one indicator is selected), one 2-D idiom rather than a thresholds-grid plus a separately-styled weight row. Rejected: **full-width side-by-side `st.columns`** (the page width divides by goals and then by the 4-column row, squishing every threshold input to ~1/18 of the page at three goals); a **per-goal expander** and a **fixed-height scroll box**; **metric-named tab labels or per-tab error badges** — `st.tabs` has no `key` and the active tab is client-side state preserved only while the label list is stable, so any label that changes on interaction snaps the user back to the first tab (hence the stable `"Goal N"` labels and the below-tabs exclusion summary instead of a badge). Full width is layout intent (Panel 3 spans below the top two columns), not a nesting constraint — inside a tab the threshold grid is the only `st.columns` level.

- **CI pins `ruff` exactly, but not `mypy`** (`.github/workflows/ci.yml`): the lint job installs `ruff==0.15.21`, an exact pin that inverts the `>=` floor convention `requirements.txt` uses for libraries. A formatter is not a library: `ruff format`'s output is version-dependent, so a floor (`ruff>=0.15.21`) would still let CI install a newer ruff that reformats untouched code and reddens an unrelated PR — determinism needs `==`. Two consequences to know before bumping: (1) `ruff check` and `ruff format` are the **same binary**, so the pin freezes lint rules alongside formatting — a version bump is one deliberate, reviewable action that may bring new lint findings and reflows together, not a silent drip of new rules. (2) `mypy` is left **unpinned** on purpose (`pip install pandas mypy`): a checker's version drift usually surfaces real type bugs you want to adopt, whereas a formatter's drift catches nothing — so the noise-generator is pinned and the bug-finders stay live. A `requirements-dev.txt` shared by CI and local was considered and rejected as churn: it would close the local-vs-CI drift gap (a contributor's own ruff can still differ from the pin) but at the cost of a new file and a change to the documented per-job inline-install shape, for a papercut a contributor hits once. The pin's single home is `ci.yml`; a contributor matches by reading it.

- **`core/bpmn/validate.py` — the XORSplitAutomation trust verifier** (in the run path: `verify_fragment` is `prepare_experiment`'s gate via `verify_transformed`; the CLI and behavioral mode remain maintainer tools): four load-bearing decisions, plus the in-path consequence at the end. (1) **Oracle independence** — a verifier that shares the code-under-test's logic proves nothing, so `validate.py` imports *neither* `query.py`'s flow helpers (`flows_from`/`flows_targeting`) *nor* `core.transformations`; it re-declares the BPMN format facts (`_BPMN_NS`, `_TASK_LOCALNAMES`) and re-encodes the pattern facts (`_BOT_NAME_PREFIX = "Auto "`, the expected topology) as its own literals, and builds its own adjacency (`_Graph`) from raw `sourceRef`/`targetRef`. A transform rename must surface as a **loud Layer-2 failure**, not silently update the oracle in lockstep (the sentinel-literal precedent, one level up). The oracle anchors on the caller-supplied target task name and walks the fragment outward by element **type + edge degree**, so it needs no gateway names; `_Graph.is_gateway`/`is_task` own the node-type policy. (2) **ERROR vs WARNING tiering** — ERROR = executability (no dangling refs; the exact expected sequenceFlow topology — what Prosimos routes on); WARNING = representation drift Prosimos ignores (`<incoming>`/`<outgoing>` lists that contradict the edges, and diagram-edge consistency). Layer 2 asserts **zero violations** (`result.violations == ()`), not merely zero errors — the real transform maintains the ref lists (next bullet), so it emits no WARNING either; asserting the stricter thing is what makes a future regression in that maintenance fail here. (3) **Behavioral proportions are conditional + the tolerance is sample-size-aware** — the target may sit on a *conditional* path, so not every case reaches the fragment: `pct_auto = bot/(bot∪human)` (of cases that entered the split), `pct_ok = 1 − (bot∩human)/bot` (of cases that took the bot branch) — dividing by the whole population undercounts (a bug the live smoke test caught, invisible to the always-reached test fixtures). Each check's band is `max(floor, sigma·SE)` with `SE = √(p(1−p)/n_eff)` and `n_eff` the *conditional* count (`reached` for pct_auto, `bot` for pct_ok), so a rare fragment / minority branch widens the band (never below the 0.05 floor) — real miswires (tens of pp off) fail while sampling noise passes. (4) **Two-layer test strategy** — Layer 1 (`TestOracleTrust`) trusts the oracle via hand-authored goldens — a minimal synthetic one (`tests/bpmn/fixtures/golden_transformed.bpmn`) and a real-scale, independently-authored Apromore model (`golden_claims_apromore.bpmn`, denoised of its `qbp:` simulator-config block), both **not** `apply_pattern`-generated (independent sources of truth — the second authored by a different person than the oracle, so it catches a self-authored golden's blind spots) plus in-test mutations asserting specific violation codes; Layer 2 (`TestAppliedPatternVerified`) spends that trust by running real `apply_pattern` (minimal fixture + demo model) through the now-trusted oracle. Behavioral mode is CLI-only (Prosimos venv, excluded from the coverage floor like `runner.py`); its pure helpers (`_observed_proportions`, `BehavioralCheck.tolerance`, `_configured_probability`) are unit-tested. **In-path consequence: a false ERROR now blocks legitimate runs**, so the verifier's own correctness bar rose with the gate. The mitigant is the existing two-layer strategy — Layer 2 asserts `violations == ()` on the real applied pattern (minimal fixture + demo model), so a regression that would false-positive in production fails the suite first; WARNINGs deliberately log to `validation.log` without raising (the transform emits none today, and blocking on representation drift Prosimos ignores would be a false-positive class by construction).
- **`<incoming>`/`<outgoing>` ref-list maintenance is uniform** (`core/bpmn/edit.py`): BPMN nodes carry redundant `<incoming>`/`<outgoing>` child lists alongside each `sequenceFlow`'s `sourceRef`/`targetRef`. `edit.py` maintains them on **every** flow it adds or retargets — `add_flow_el` links both endpoints, `update_flow_target` unlinks the old target and links the new one — so a model stays internally consistent after an edit. Three decisions. (1) **Uniform, not source-matching.** The alternative ("write the lists only where the source model already used them") has no stable target: BPMN *dialects* disagree (Simod/ProM omit them on tasks but write them on gateways/events; Apromore writes them everywhere), so "the convention" is per-element-type and per-tool, and matching it means re-deriving it per model. Uniform maintenance is one rule, and the schema permits it everywhere — the lists are `minOccurs="0"`, so writing them is always legal and *omitting* them is never a lie. The invariant bought: **a BPMN stays stable under `edit.py`** — what goes in consistent comes out consistent. (2) **The defect fixed was the *lie*, not the omission.** Pre-fix, `update_flow_target` wrote only `targetRef`, so a retargeted flow left its *old* target claiming an `<incoming>` it no longer receives — a contradiction, distinct from the (schema-legal) omission on the new target. This is why `validate.py`'s `IO_LIST_DRIFT` flags contradictions but not absences, and why it stays a **WARNING**: Prosimos routes off the refs and ignores the lists (a real run confirmed the stale entry was harmless), so the tier tracks **impact**, not authorship. (3) **The child-order trap.** `tFlowNode` orders its children — header elements, then `incoming*`, then `outgoing*`, then subtype content — and `incoming`/`outgoing` being optional does **not** make them unordered. A bare `SubElement` append would land an `<incoming>` after an existing `<outgoing>` and produce a schema-invalid model, defeating the exact spec-strictness this maintenance exists to serve; `_insert_flow_ref` therefore computes an insert index and is idempotent (re-linking an unchanged endpoint never duplicates a ref). Verified by `TestFlowRefMaintenance` (`tests/bpmn/test_edit.py`) and, end-to-end, by `validate.py` reporting 0 violations on the transformed demo model where it previously warned.

A second Transformation pattern will never be added, so the original "wait for a second pattern" argument is moot; the extraction is justified by the existing architectural boundary. - **First-principles metrics + trust checker** (`core/simulation/prosimos/calendars.py`, `replication_metrics.py`, `runner.py`, `orchestrator.py`, `core/simulation/validate.py`): every product metric is derived from the **event log + params JSON**; the stats CSV is not a product source — it is the *checker oracle* (the first-principles derivation itself was the client decision, 2026-07-20). **Cost**: the naive `(end−start) × rate` over-counts ~9× because `[start, end)` is wall-clock while Prosimos charges *working* time only; intersecting each event with its resource's weekly calendar reproduces Prosimos's cost — **exactly, to the cent** (the ~0.02% "residual" earlier spikes saw was our own overlap double-count: discovered calendars carry overlapping periods and `WeeklyCalendar` merges them to the union, which is what Prosimos charges; do NOT attribute a residual to "granule" — `granule_size` is fuzzy-engine-only, these models are crisp). **One clock** (2026-07-23): every cycle number anchors **first-task-start → last-task-end** — the log-based case duration Celonis (`CASE_START` = first activity of the case) and Apromore (log start→end timestamps) report — and `total_cycle_s` is the per-case sum, so `total = mean × n × 3600` holds by construction in both modes. The head wait (arrival → first task start: Simod's extraneous-delay timer — an `intermediateCatchEvent` consuming its own sampled delay — plus pre-first-task queueing) is insensitive to automating the target, so it stays out of the ranked clock; door-to-door lead time (arrival → completion) is **deliberately unmeasured**, with the visible give-up recorded in docs/metrics.md — the arrival is absent from industry-normal logs (left truncation), unrepresentable in Simod's input schema, and not exported to our event logs. **Rejected: `--is_event_added_to_log`** (removed 2026-07-23; it had been passed on the maintainer's own assumption that the total should be arrival-anchored — NOT a client decision). The flag's sole product value was surfacing the arrival as intermediate-event rows (`resource == "No assigned resource"`); rankings/cost/rework compute over task rows and are bit-identical without it, while the phantom `Event_<uuid>` rows polluted every exported log (49% of rows in a real P2P model — external tools discover them as fake activities) and forced a mandatory event/task split (unfiltered, looped timers count as rework and zero-length event spans drag `min_cycle_h`). If ever reconsidered: Prosimos parses the flag's value truthily — even `"false"` enables it — so omission is the only off state, and `replication_metrics` raises a named ValueError on a flag-on log rather than mis-parsing it. **Rejected: arrival-anchored `total_cycle_s`** — dies with the flag; the arrival-anchored aggregate stays readable by hand in each run's stats CSV (`idle_cycle_time`), demoted from product metric to manual diagnostic. **Checker consequence**: the arrival-cycle and arrival-window checks died with the flag — the cycle dimension is unchecked (Prosimos's `cycle_time`/`idle_cycle_time` are both arrival-anchored, so no oracle exists for a first-start clock; verified on goldens that `idle_cycle_time = cycle_time + idle_time` exactly, i.e. there is no third, first-start-anchored KPI hiding in the stats), while cost/working-seconds reconcile the same start/end columns the cycle reads and the exact case count doubles as a vanished-case detector. **The checker's oracle-inversion** (`validate.py`): unlike `bpmn/validate.py` (both sides our code → re-encode expectations), here the oracle is a foreign codebase's accounting, so the checker *imports* the product engine — re-deriving would verify a sibling, not the product; independence lives in the oracle. Cost indicators (min/max/median) are the follow-up — the per-case series exists; adding them is the documented ~4-file recipe.
- **Rework and bot-failure KPI semantics** (`core/simulation/prosimos/replication_metrics.py`, client requirements 2026-07): bot failures are **not rework** — they are their own output metric. (1) **Rework** (`COL_TOTAL_REWORK_COUNT`, `COL_REWORK_RATE`) counts repeated-activity work only: for every (case, activity) pair where the activity appears more than once, `occurrences − 1`; a case visiting "Fix Bug" three times contributes 2. `COL_REWORK_RATE` is a percentage (0–100) of cases with any repeated-activity rework. `_rework_metrics(event_log)` needs no task names — repeated-activity counting is name-agnostic. (2) **Bot failures** (`COL_TOTAL_BOT_FAILURE_COUNT`): `_bot_failure_count(event_log, bot_task_name, original_task_name)` counts cases where both `"Auto X"` and `"X"` appear (bot ran, human redid the work) — binary per case, so a case counts once regardless of loops. **Count only, no rate**: every rate variant is input-derivable in expectation (over bot attempts ≈ `100 − pct_ok`; over all cases ≈ `pct_auto × (1 − pct_ok)`), so a rate would echo configuration back at the user. **Not rankable** for the same reason — a "minimize bot failures" goal would reward low `pct_auto`/high `pct_ok` config, not simulation discovery; `BOT_FAILURE_COUNT` mirrors `REWORK_COUNT` (`indicators=()`, `rankable=False`, Baseline tab + exports only) and omits `pct_change_name` because the baseline value is structurally 0 (no case reaches the bot at 0% automation), which would make a percent column permanently blank. The demo formulas split accordingly: expected bot failures = `pct_auto × (1 − pct_ok) × n_cases`; demo rework scales with `expected_human_fraction` (direct-path + failed-bot redo cases), mirroring the cost model's human-fraction logic. pm4py was rejected for rework counting: it provides only a binary per-case per-activity flag and no process-wide rate. A missing `"activity"` column (e.g. synthetic test CSVs) returns zeros rather than crashing, in both helpers.
- **`compare_to_baseline` and `aggregate` are data-driven** (`core/analysis.py`): `compare_to_baseline` iterates `MetricRegistry.all()` aggregate specs to build each display row — adding a new metric requires only a new `Metric` entry in `MetricRegistry`. `aggregate` uses pandas named-aggregation syntax (`output_col: (source_col, aggfunc)`) with no conditional guards; all metric columns are always present in both the demo and real pipelines. `_pct_delta(delta, baseline)` returns `nan` when `baseline == 0` (mathematically undefined percentage, surfaced as a blank cell — the right call for a display helper, not a logic-error path that should raise).
- **`MetricRegistry` architecture** (`core/metrics.py`): `Metric` is a frozen dataclass composing `tuple[IndicatorSpec, ...]` and `MetricSpec | None` — composition over inheritance. `rankable: bool` and `sn_floor: float` live on `Metric` (policy decisions about the metric as a whole): `rankable` controls whether the metric appears in the ranking dropdown; `sn_floor` controls whether zero is a valid outcome for S/N computation. `upper_bound: float | None` lives on `IndicatorSpec`, not `Metric` — the value-domain ceiling is a fact about an indicator's own values (only the rework-rate indicator sets it, 100.0 — a percentage of cases; it drives the goal-threshold widgets' `max_value` and seed clamp). `MetricDirection(str, Enum)` eliminates the magic strings `"smaller_is_better"`/`"larger_is_better"` while remaining compatible with `signal_to_noise(direction=...)` since `MetricDirection` is a `str` subclass. `_identity` and `_seconds_to_hours` are named functions (not lambdas) so they are picklable — relevant if `MetricSpec` objects ever pass through `multiprocessing` or `@st.cache_data`. `display_fn` and `direction` are defaulted fields on `MetricSpec` (`_identity` and `SMALLER_IS_BETTER` respectively) so most specs need only three required fields. The goal selector (`ui/interactive/goal_config.py`) reads `MetricRegistry.rankable()` directly and relies on `Metric` being hashable (a frozen dataclass whose fields are a tuple of frozen `IndicatorSpec` dataclasses over `NamedTuple` specs) for its `metric not in chosen_metrics` membership test — class-level constants are stable module-level singletons.
- **Per-case accessors raise instead of returning `None`** (`core/metrics.py`, `ui/table.py`, `ui/interactive/main_effects.py`): `per_case_column`/`per_case_display_name`/`per_case_compact_label` return non-Optional `str`, raising `ValueError` via the `default_indicator` property when a metric has no indicators — true of `REWORK_COUNT` and `BOT_FAILURE_COUNT`, neither of which is rankable, so every legitimate caller (all gate on `rankable()`) never trips it. Raising spares consumers the assert-narrowing mypy would otherwise force — mypy cannot express the rankable→has-indicators invariant, so a None return would re-impose per-call-site asserts (`ui/table.py`, `ui/interactive/main_effects.py`); `tests/test_metrics.py` pins the raise. A `RankableMetric` subtype (static proof instead of runtime raise) was considered and rejected: narrowing a dataclass field type in a subclass violates mypy's attribute invariance (fields aren't read-only to the type system, even on frozen dataclasses), and it would reverse the documented composition-over-inheritance design above. Raising matches the existing precedent in `Goal.from_indicator` and `analysis.main_effects` — both keep their own no-indicators guards, which produce call-site-specific messages at their function boundaries.
- **`ParameterKind` is a `Literal`, not an `Enum`** (`core/parameters.py`): `ParameterKind = Literal["percentage", "duration_s", "cost", "categorical"]` is the named alias for `Parameter.kind`. Kept as a `Literal` (not `str, Enum` like `MetricDirection` above) because its usage profile is the opposite: `kind` is a declaration-time tag — set as a bare string at ~12 call sites (`XORSplitAutomation.parameters()` + test fixtures), all mypy-validated against the alias — and branched on in exactly one consumer (`number_input_kwargs` in `ui/param_inputs.py`); it never flows through layers, is never iterated or serialized. The `Enum`'s distinctive wins (namespaced access, iteration, attached behaviour) don't apply, and attaching the per-kind `st.number_input` config to a `core/` enum would pull Streamlit into the domain, breaking the `ui → core` layering. `MetricDirection` is an `Enum` because it *flows* — set on `MetricSpec.direction`, passed by name through `signal_to_noise`/`main_effects`, referenced ~15× — a genuinely different profile, so matching the structure purely for consistency would be cargo-culting. One accepted trade-off: under default mypy the `kind == "..."` comparisons inside `number_input_kwargs` aren't typo-checked (a `Literal`-vs-non-member-string comparison isn't flagged without `--strict-equality`); low risk because the four branches sit beside the alias and `tests/ui/test_param_inputs.py` pins each kind's kwargs.
- **`COL_REWORK_RATE` stored as percentage (0–100) throughout `core/`** (`core/simulation/prosimos/replication_metrics.py`, `core/demo.py`): `_rework_metrics()` multiplies the fraction by 100 at the source; `BASELINE_REWORK_RATE = 5.0` in `demo.py` is in percentage units. All `display_fn` values for rework rate are therefore `_identity` — no fraction↔percent bridge exists anywhere. Tradeoff: changing storage unit required touching three modules — judged worthwhile because a fractional storage unit with display-time conversion is a leaky abstraction where every new consumer must know to multiply by 100.
- **`COL_*` metric column naming convention** (`core/constants.py`, `core/simulation/prosimos/replication_metrics.py`): per-case mean metrics are prefixed with `mean_` (`COL_MEAN_CYCLE_H`, `COL_MEAN_COST`); process-wide sums are prefixed with `total_` (`COL_TOTAL_CYCLE_S`, `COL_TOTAL_COST`, `COL_TOTAL_REWORK_COUNT`); pure rates/ratios that are already scale-independent carry no prefix (`COL_REWORK_RATE`). The corresponding `_MEAN` aggregation constants follow the same pattern (`COL_MEAN_CYCLE_H_MEAN`, `COL_TOTAL_REWORK_COUNT_MEAN`, etc.). `ReplicationMetrics` field names mirror the `COL_*` string values so `dataclasses.asdict()` produces correct DataFrame column keys without an explicit mapping. The prefix convention prevents silent semantic errors — a reader can tell at a glance whether a column contains a per-case value or a sum that scales with the run's case count (`n_cases`).
- **Panel 5 ranked table column readability** (`app.py`): `scenario_id` column header renamed to `"Scenario"`. KPI columns renamed from raw column names (e.g. `mean_cycle_h_mean`) to display names (e.g. `"Cycle Time (h/case)"`) via a rename map derived from `MetricRegistry.all()` — no second copy of labels. Factor columns renamed via `{p.id: p.label for p in params}` as before.
- **Demo extraction — `demo.run_experiment()` owns all synthetic logic** (`core/demo.py`, `core/orchestrator.py`, `app.py`): a `demo_mode: bool` threaded through `orchestrator.run_experiment()` is the rejected shape: it scatters `if demo_mode:` branches across the prepare/apply/simulate/collect steps, makes every new demo metric a two-file touch (`demo.py` formula + `orchestrator.py` placeholder), and leaves the orchestrator as the real pipeline plus a synthetic bypass. Instead `demo.py` owns the full synthetic loop via its public `run_experiment(scenarios, n_reps, n_cases, on_progress) -> ExperimentResult`; `orchestrator.run_experiment()` is a straight real-pipeline path; `app.py` makes one explicit routing decision at the call site. Key design choices: (1) `DemoResult` becomes private `_SimResult` mirroring `ReplicationMetrics`' fields — `total_cycle_s = mean_cycle_h × 3600 × n_cases`, `total_cost = mean_cost × n_cases`; the current rework/bot-failure formulas are documented in the rework-and-bot-failure bullet above; (2) the `ExperimentResult.baseline_agg` a demo run commits stays `None`, so only the Baseline tab's baseline-*comparison* view is gated on real mode; goal-config baseline still works in demo via the standalone `demo_baseline_agg()` (`app.py` resolves `per_case_baseline` from it), so it is the Baseline tab's baseline *reporting*, not demo baseline support in general, that is future work; (3) `ExperimentResult` stays in `orchestrator.py` — `demo.py` imports from it without a cycle because `orchestrator.py` no longer imports from `demo`; (4) demo discovery is no longer faked — `app.py` points the demo `LogIdentity` at the pre-baked `demo/` model (`DEMO_BPMN`/`DEMO_JSON`) and reuses the real `list_activities` + factor-prepopulation path (the activity dropdown and per-activity discovered durations come from the demo fixtures).
- **`Parameter.id` carries no activity-name prefix** (`core/transformations.py`, `core/parameters.py`, `core/demo.py`): `Parameter.id` is a bare factor key (e.g. `"pct_auto"`) with no `"{activity}."` prefix. The prefix was removed because: (1) within a single experiment there is only ever one target activity, so the prefix adds no disambiguation; (2) it caused a double-prefix trap in `factor_label_map` where `p.id` already contained the full key but callers tried to prepend the target activity again; (3) it polluted the results DataFrame column names with the activity name, making them unreadable in the ranked table. The activity name is available in session state (`ss.target_activity`) for any display use. Factor IDs are defined as named constants (`F_PCT_AUTO = "pct_auto"` etc.) in `constants.py` — they're consumed by `transformations.py` and `demo.py`, satisfying the cross-module rule. `AutomationParams.from_taguchi_values()` uses direct key lookup (`values.get(F_PCT_AUTO, default)`) rather than the previous suffix-scan (`k.endswith("." + suffix)`) which would have silently fallen back to defaults with bare keys.
- **Bot cost as experiment-wide input** (`app.py`, `core/transformations.py`, `core/orchestrator.py`, `core/demo.py`): `bot_cost_per_hour: float = 0.0` is treated as a scalar experiment config (like `n_reps`) rather than a Taguchi factor — it applies uniformly to every scenario and doesn't belong in the orthogonal array. Units are $/hr to mirror Simod's cost model. Default 0.0 preserves the prior zero-cost behaviour without a breaking change. Prosimos stores `cost_per_hour` as a string in the resource JSON (confirmed from Prosimos source); the conversion `str(bot_cost_per_hour)` happens at resource-dict construction in `build_scenario_template`. The demo formula replaces a prior magic `0.6` constant with a principled derivation: `expected_human_fraction = (1 − pct_auto/100) + (pct_auto/100) × (1 − pct_ok/100)` (humans handle all non-automated cases plus bot failures); `bot_cost_per_case = (pct_auto/100) × (t_auto / 3600) × bot_cost_per_hour`. This correctly models that bot failures redirect to the human path, avoiding silent cost underestimation at low `pct_ok` values.
- **`ScenarioParams` / `AutomationParams` pairing** (`core/parameters.py`, `core/transformations.py`): `Transformation` ABC is paired with `ScenarioParams` base class — each concrete `Transformation` subclass has a corresponding `ScenarioParams` subclass holding its typed simulation inputs. `AutomationParams` is `XORSplitAutomation`'s concrete params class; it lives in `transformations.py` alongside the pattern that owns it. `Transformation.apply_params` is typed `scenario: ScenarioParams`; the concrete override asserts `isinstance(scenario, AutomationParams)` at entry for runtime safety without narrowing the override signature (which mypy would flag as a Liskov violation). `AutomationParams` is derived FROM a `Scenario` (via `from_taguchi_values()`), not a sibling of it — it is the typed interpretation of a Scenario's raw Taguchi values for the XOR pattern. `ScenarioParams` is a plain base class (no abstract methods); it's a semantic marker, not a protocol. `params_from_values(values, result) -> ScenarioParams` on the ABC is the bridge that keeps `orchestrator.py` free of any concrete `AutomationParams` import — the orchestrator calls `transformation.params_from_values(s.values, bpmn_tr)` and never touches the subclass directly. `selected_resource_id` is a typed field on `BpmnTransformResult` (not an opaque `Any` context) because it is meaningful at the boundary and applies to any automation pattern that varies a human resource pool. n_reps does not go into `BpmnTransformResult` because the transformation layer never uses it — it is consumed entirely by the orchestrator's task-building loop.
- **Parallel simulation** (`core/simulation/executor.py`, `core/orchestrator.py`): all scenario and baseline replications execute in a single `ThreadPoolExecutor`. `Popen.wait()` in `runner.simulate` releases the GIL, giving true OS-level parallelism — `ThreadPoolExecutor` was chosen over `ProcessPoolExecutor` (no benefit for subprocess-bound work; adds serialization constraints) and `asyncio` (propagates `async def` through the call stack, risky Streamlit integration). Scenario JSONs are pre-generated sequentially before any worker starts — XML/JSON mutation is not thread-safe. `wait(FIRST_COMPLETED)` is iterated on the calling thread so `on_complete` and `on_error` can mutate shared state without locks; `wait()` replaces `as_completed()` to allow dynamic future re-submission for retries. Individual failures are retried up to `task.max_retries` times before calling `on_error` — see the failure recovery decision below. Baseline and scenario tasks share one pool. Progress total includes the baseline replications (`len(scenarios) × n_reps + n_reps`).
- **`executor.py` extraction from `orchestrator.py`** (`core/simulation/executor.py`): execution details (thread pool, worker count, `as_completed`) are hidden from `orchestrator.py` behind `run_all(tasks, on_complete, on_error)`. `SimulationTask` carries the full per-replication context (`bpmn_path`, `json_path`, `n_cases`, output paths, typed `metadata`) so `on_complete` can read output files without needing a separate lookup. The fields mirror `runner.simulate`'s signature but `executor.py` treats them as a unit of work — it doesn't reason about BPMN paths or case counts, just forwards them. `metadata: Any` is intentionally opaque to the pool; the orchestrator sets and reads it, and the pool passes it back unchanged.
- **Simulation failure recovery — retry with continue-on-error fallback** (`core/simulation/executor.py`, `core/orchestrator.py`, `app.py`): `SimulationTask` carries `max_retries: int = 0`; `run_all()` decrements it on failure and re-submits the task to the same pool via `dataclasses.replace`. Only when `max_retries` reaches 0 does `on_error` fire. The orchestrator passes `max_retries=2` (3 total attempts) to every task, configurable via `run_experiment(max_retries=...)`. `on_error` is the continue-on-error fallback for permanently failing tasks: the orchestrator's `_on_error` closure appends a `FailedReplication` and ticks progress. After all tasks finish: if every scenario replication permanently failed (empty `rows`), `SimulationError` is raised; otherwise a partial `ExperimentResult` is returned with `failed_replications` populated. `baseline_agg` is returned as `None` (not `{}`) when all baseline replications fail — an empty dict is falsy and would cause `ss.baseline_agg if ss.baseline_agg is not None else demo.demo_baseline_agg()` to silently substitute demo constants for goal targets in real mode; `None` is the unambiguous sentinel. Panel 5 shows a `st.warning` when the committed result's `failed_replications` is non-empty; the Baseline tab shows an explicit `st.warning` in real mode when `baseline_agg is None`. Disk-based checkpoint/resume was considered and rejected: requires a resume UI surface, session-state matching across runs (fragile when the user changes params), and significant infrastructure. `FailedReplication.task_kind` deliberately omitted — `scenario_id` doubles as the species label (a scenario id, `"baseline"`, or `"as_discovered"`), so a caller needing to distinguish tests it directly. Typed metadata: `BaselineMeta(rep)` (frozen=True) and `ScenarioMeta(scenario_id, rep, values: dict[str, object])` (plain `@dataclass` — `frozen=True` on a class with a mutable dict field only prevents field rebinding, not dict mutation, giving a false safety guarantee) replace opaque tuples. `_on_complete` dispatches on `isinstance(meta, BaselineMeta)` directly with `assert task.out_stat is not None` hoisted above the branch; `_unpack_meta` is retained only for `_on_error`. `run_all()` wraps the entire callback dispatch block in `try/except Exception: pool.shutdown(cancel_futures=True); raise` — a callback exception cancels all pending tasks. A shared `_tick(label, rep)` inner function eliminates the duplicated progress-tail.
- **New module creation rule**: prefer a new file when the concern is genuinely distinct enough to deserve its own mental model — a clear boundary (domain type, display context, execution concern) earns a new module. The trigger is whether the concern has a distinct identity, not whether the code is extractable. A small helper with no distinct purpose belongs in the nearest related existing module; non-trivial logic with a clear boundary belongs in its own file. Module boundaries are cheap to reason about but expensive to dissolve later — err on the side of separation when the identity is clear.
- **Comment hygiene — the verifiability test** (repo-wide; applies to inline comments, docstrings, and §8 bullets alike): a comment earns its place when the next reader can **check it against the code in front of them plus knowledge of the domain**. If confirming it would take git archaeology, it is unfalsifiable and already rotting — it belongs in a commit message or PR body, which are **dated by construction** (nobody reads a commit from March expecting it to describe today; every reader of a docstring does). Write the constraint, not the changelog. *"A whitelist would have to enumerate every task/gateway/event subtype and would reject valid models on the ones it missed"* is checkable against `BPMN_TASK_TAGS` → keep. *"Re-checking the plane per call is what produced the bug this shape replaced"* needs `git log` → cut from the docstring; the durable half (reject-not-tolerate, and why tolerate loses) is already a §8 bullet, and the narrative half belongs to the commit.
  **The useful gradient: comments that cite the *domain* outlive comments that cite our *code's shape*.** Observed decay, fastest-rotting last — *"an `<incoming>` parented on a `<sequenceFlow>` is schema-invalid"* (pure BPMN; cannot rot, we don't own the fact) → *"`_link_flow_refs` looks up process nodes while `_waypoints_between` looks up DI shapes"* (names our symbols; survives until a rename) → *"`add_flow_el` keeps `root` for waypoint geometry"* (pure code shape; **was false within the hour**, invalidated by the very next commit on its own branch). Prefer the first kind: a fact about BPMN does not drift when we refactor.
  **The failure mode is comments nobody changed, not comments badly changed** — so "scrutinise comment diffs" is the wrong guard. That stale `root` claim was not a botched edit; it sat untouched in §8 while a *different file* moved out from under it, and only a grep found it. A comment invalidated at a distance has no review event to catch it, which is the whole argument for the gradient above: prefer prose that *cannot* be invalidated from elsewhere. When a change does move code that prose elsewhere describes, grep for the moved symbol before finishing — §3's module map and §8's bullets both name symbols and both go stale silently.
  **When a comment must change, re-derive it from the current code — don't patch the old text.** Inline edits keep the old framing and accrete, the sedimentary changelog the test above rejects, so rewriting the *comment* (not just the stale clause) lands tighter. Exception: a change that swaps only a referenced token (a version, a renamed symbol) while the claim holds is a surgical edit — a rewrite there is wasted churn, and risks deleting rejected-alternative prose the code can't restore. This rewrite *is* the verifiability test at edit time: a constraint comment reproduces from the code, so a rewrite recovers it; prose you can't reproduce is a rejected-alternative to keep on purpose or narration to cut. `/doc-rot` and `/doc-audit` hunt the narration and redundant-restatement forms of this; `/triage-findings` re-derives on fix and holds prose cuts for confirmation.
  **This bullet indicts §8 hardest, deliberately.** §8 is large, undated, and is precisely the historical-rationale store; the coverage-boundary note above records a 34-PR session-log lapse that cost little — the design record, not the narrative, was the load-bearing half. §8 earns its place where it holds **rejected alternatives** — the re-litigation shield the code cannot express — and should shed the rest. A §8 entry that narrates *what happened* is a commit message in the wrong file.
- **Code-review rubric — Craft vs Structure** (canonical list; the `quality-pass` command's two agents anchor here): quality findings — distinct from *correctness* — split on an **intrinsic-vs-relational** axis. **Craft** ("is it *written* well?" — judgeable from the hunk in isolation): **DRY / reuse** (no duplication, internal or external — reuse is DRY's external face) · **readability** · **simplification** (remove unnecessary complexity) · **side-effect discipline** (Command-Query Separation; core-layer purity; workers never touch `st.*`) · **consistency** (match the neighbourhood's idioms/vocabulary — the mirror-module discipline, `discovery_manager` ↔ `run_manager`; a straddle: relational *input*, surface *target*). **Structure** ("is it *shaped / placed* well?" — needs the architectural map: §2 seams, §3 module map, the `ui/` layering rules): **Separation of Concerns / cohesion** (one unit = one job; related parts together; behaviour with its owner — the *lateral* "right house" question; absorbs responsibility-placement as a strict sub-category) · **Law of Demeter** · **dependency direction** · **abstraction depth / information hiding** (deep modules; flag shallow pass-throughs) · **change amplification** (one conceptual change → few edit sites — the single reset helper, the data-driven `MetricRegistry`) · **altitude** (right *depth* of a fix — *vertical*; not a bandaid on shared infra) · **hook-economy** (is a structural change worth its churn — the governor; its retrospective face is YAGNI / speculative-generality) · **behavioral subtyping / Liskov** (low-frequency — fires on the `Transformation` ABC override). **Correctness / robustness / concurrency-safety / performance / security are a *separate dimension* ("is it *right*?") owned by `/code-review`, not this rubric** — which is why the pass is two-class, not three (concurrency-safety appears here only as a Structure *invariant*, the threading rules; as a bug it belongs to `/code-review`). Two candidate axes were merged out as strict sub-categories: responsibility-placement ⊆ SoC (the "right owner" question *is* concern-ownership), and reuse = the external face of DRY.

The rule is one line and structurally enforceable: **only modules under `ui/interactive/` may import streamlit; every other `ui/` module stays Streamlit-free.** The pure primitives deliberately keep the `ui/` top level rather than getting a third `ui/display/` folder: once the renderers (`ui/interactive/`) and the services (`ui/services/`) are housed, the residual top level is homogeneous, and moving three pure modules would be churn for symmetry — the same judgment that originally kept the whole Streamlit-free population at the top level until the services/primitives distinction earned its own location (drawn for handoff legibility; the enforceable invariant remains the streamlit-import line alone). The category is **not** speculative-for-one: the Panel 2 factor-levels grid (`ui/interactive/factor_levels.py`), the Panel 5 main-effects charts (`ui/interactive/main_effects.py`), the Panel 5 ranked-scenarios table (`ui/interactive/ranked_scenarios.py`), the sidebar's Simod preflight panel (`ui/interactive/simod_preflight.py`), the Panel 4 execution panel (`ui/interactive/execution_panel.py`), the Panel 3 goals block (`ui/interactive/goal_config.py`), the sidebar discovery-progress fragment (`ui/interactive/discovery_panel.py`), the shared failure surface (`ui/interactive/error_surface.py`), the sidebar discovery-config group (`ui/interactive/discovery_config.py`), and the model-fidelity panel (`ui/interactive/fidelity_panel.py`) are the rest of its tenants, and `app.py` still inlines more (the export row) — natural future tenants that land as their own focused extractions, justified the moment the category is proven by the inlined instances (a category recurs whether its instances are extracted or still inlined). Several of these also realise the **two-tier** dependency — interactive components importing `ui/`-parent primitives (`factor_levels → param_inputs`, `main_effects → plots`, `ranked_scenarios → table`, `simod_preflight → preflight`, `execution_panel → run_manager`, `discovery_panel → discovery_manager`, `fidelity_panel → run_manager + table`) — so the dependency *within* `ui/` flows `ui/interactive/ → ui/services/` + the `ui/`-parent primitives, and the whole shape reads `app.py → ui/interactive/ → ui/services/ + ui/ primitives → core/`. `param_inputs`, `plots`, `table`, and `preflight` are consumed only via their components — `run_manager` is the one exception: `app.py` still imports `cancel_experiment`, `clear_results`, and `clear_as_discovered` directly (all for `_clear_process_state()`, the log-scoped reset helper), because they are used *outside* the run panels' boundary; the remaining run-lifecycle functions moved fully behind the two run panels (`execution_panel` and `fidelity_panel`, the shared lifecycle's kind-routed consumers). A module can be a two-tier dependency for one caller and a direct dependency for another — the partition tracks *which functions* an outside caller needs, not an all-or-nothing per-module rule. `ranked_scenarios` and `simod_preflight` differ from their other siblings in one respect: they return a value (a `DataFrame`, a `(bool, str | None)` tuple) rather than `None`, because `app.py` still needs the result downstream (Statistics CSV export; `preflight_ok`/`java_home` for the discovery gate) — a component's return type is whatever the caller genuinely needs back, not uniformly `None`. `execution_panel` also carries a Streamlit polling fragment (the module-level `_render_run_progress`, a `@st.fragment(run_every=...)` poller mirroring `discovery_panel`) and the background-thread discipline (session-state snapshots into locals before the thread starts) — the extraction was a verbatim move of that discipline into an importable function, not a new pattern. Tradeoff accepted: an `st`-calling component's rendering is exercised manually like `app.py`; any pure helper a component carries must be unit-tested (`error_surface.error_log_tail` is the current instance), and a pure helper that gains a second consumer moves to the `ui/` parent — the extraction buys readability, altitude (`app.py` becomes more purely a composition root), and a typed `ResourceSelection` contract, **not** test coverage. The component is "smart": it calls `resource_pool_size` (core) itself and owns `_halt_if_unresolved`, returning a complete validated `ResourceSelection`. Note this is a new *role within the UI layer* (interactive component), not a new architectural layer — the dependency direction is unchanged (`app.py → ui/ → core/`); `resource_selector` sits beside `table.py`, not between `app.py` and `core/`.
- **Deferred `DiscoveredContext` abstraction** (`app.py`, `core/transformations.py`): `parameters()` takes three loose Simod-discovered scalars (`current_duration_s`, `selected_pool_size`, `frozen_pool_size`) that prepopulate factor levels — the `task → mean_time` and `resource → pool_size` lookups (both in `prosimos/query.py`). Bundling them into a `DiscoveredContext` dataclass was considered and **deferred**: with only two inputs and one fixed-factor pattern it is a shallow results-bundle (different keys, no shared computation — the genuinely reusable layer is already `prosimos/query.py`), it would not help the widget-key fix (per-level `p.levels[i]` keying is strictly more precise than a shared-context hash, which would reset *every* factor including fixed ones on any change), and it would not remove the malformed-model guard (UI surfacing via `_halt_if_unresolved`, now in `ui/interactive/resource_selector.py`, stays). The trigger to pull it in would be a **third** discovered-value input; its one candidate — a workload / arrival-variance factor — was cut as out of scope (§8), so with the pattern and its factors frozen there is no foreseeable trigger, and the abstraction stays deferred indefinitely.

- **Event log export** (`core/orchestrator.py`, `core/simulation/store.py`, `app.py`): Prosimos writes event log CSVs to disk for every replication (both scenario and baseline) via `SimulationTask.out_log`. `ExperimentResult` now tracks these as `scenario_log_paths: dict[str, list[Path]]` and `baseline_log_paths: list[Path]`, populated in `_on_complete` alongside metric parsing — so only successfully completed replications are tracked; a permanently failed one (after retries, recorded in `failed_replications`) goes through `_on_error`, not `_on_complete`, and has no log entry in the ZIP. `store.event_logs_zip()` packages them using `archive.write()` (disk-to-ZIP streaming) rather than the `.writestr()` used for small param JSONs — log files can be large. ZIP structure mirrors the on-disk layout: `scenarios/<sid>/rep_NNN_log.csv` and `baseline/rep_NNN_log.csv`. The export button is a separate "Event logs (ZIP)" in Panel 5's export row (not merged into "Model (ZIP)") — event logs are raw simulation output, not model artifacts. Disabled in demo mode (no real Prosimos output). Button label separation: "Params (ZIP)" for scenario params JSONs, "Model (ZIP)" for BPMN + params + statistics + S/N, "Event logs (ZIP)" for log CSVs — three distinct scopes.
- **Session state helpers** (`app.py`, `ui/services/run_manager.py`): the app has four implicit states — IDLE (no log), DISCOVERED (log + activities), RUNNING (background thread alive), DONE (results present). `clear_results(ss)` (in `ui/services/run_manager.py`) resets the run-level state (`ss.experiment_result` + `experiment_error`) — deliberately **not** `baseline_agg`, which is written by `commit_result` but log-scoped in validity (same discovered model → the previous run's baseline stays a correct reference mid-re-run; clearing it at run start collapsed Panel 3's threshold rows on any mid-run rerun); `app._clear_process_state()` is the shared log-scoped reset — `cancel_experiment(ss)` (a no-op when no run is active; without it a background thread could complete and write its result back into `ss.experiment_result`, silently undoing the reset) + `cancel_discovery(ss)` (kills an in-flight discovery's Simod — dropping the session without it would orphan the subprocess) + `clear_discovery(ss)` + `clear_results(ss)` + `clear_as_discovered(ss)` + `ss.baseline_agg = None` + `reset_goal_thresholds()` + `reset_goal_selection()` — called from both events after which this state would describe a different process: `app._clear_log()` ("Reset log"; adds `ss.log = None` — the whole `LogIdentity`) and the `needs_discovery` branch (uploading a different file without "Reset log" — otherwise an in-flight run could commit into the new log's session, stale results would survive the switch, and thresholds edited against process A would silently score process B). `goal_threshold_overrides` is deliberately log-level, **not** run-level: `clear_results` runs at every run start, and clearing the user's edited goal thresholds there would wipe them on every re-run — the exact UX failure the overrides dict exists to prevent (see the goal-threshold bullet below). `clear_results(ss)` is also called at run start (by `ui/interactive/execution_panel.py`) so Panel 5 goes blank immediately rather than showing stale results. New session state keys belong in one of these helpers, not scattered across reset sites. A formal FSM *library* would be overkill for these four top-level states — but the **discovery sub-flow** did earn an explicit (library-free) state machine once its states multiplied; see the next bullet.
- **Discovery state machine keyed by the upload fingerprint** (`ui/services/discovery_manager.py`, `ui/interactive/discovery_panel.py`, `app.py`): the discovery sub-flow grew to five states (idle / running / done / failed / cancelled) encoded implicitly across four independent session keys — `current_discovery` (in-flight), `discovery_settled` (an `Exception`/`"cancelled"`/None terminal marker), `log_fingerprint`, and `ss.activities`. They drifted: a cancelled discovery of file A left `discovery_settled` set and the banner gate compared it against a *separate* `log_fingerprint`, so uploading file B could leave the "Retry discovery" banner stuck instead of auto-starting B (a bug that could not even be reliably traced — the tell that the implicit machine had outgrown ad-hoc flags). Fix: one `DiscoverySession` (in `ss.discovery`) keyed by `fingerprint` and carrying the outcome state (the canonical field list lives in the §3 row), and `discovery_phase(ss, upload_fp)` as the sole router returning `RUNNING`/`FAILED`/`CANCELLED`/None. The load-bearing move is **keying the state on the upload fingerprint inside the session object**: `phase` is `None` whenever `session.fingerprint != upload_fp`, so a terminal session for a superseded upload is unrepresentable-as-relevant rather than guarded-against — the drift bug becomes structurally impossible. the committed `ss.log` remains only for the "already discovered successfully" short-circuit (its `fingerprint` field, stamped at commit); everything transitional lives in the session. This is not an FSM library — an `Enum` + one dataclass + a pure router function — consistent with the "explicit state where it earns its keep" stance above. Contrast `RunOutcome` (next bullet): the experiment run needed only the terminal-outcome discriminated union, not fingerprint-keying, because a run is launched by an explicit button, not auto-triggered by an upload identity.
- **Nested session state — `ss.log` and `ss.experiment_result`** (`ui/services/discovery_manager.py`, `ui/services/run_manager.py`, `app.py`): the two big flat key families are whole-object keys — `LogIdentity` (model paths, activities, fingerprint, upload path, Simod CSV, case count, discovery mode) and the committed `ExperimentResult`. Streamlit session state stores arbitrary objects, and the app had already proven the pattern three times (`ss.discovery`, `ss.run_state`, `ss.as_discovered_result`); the flat families' cost was real — multi-line resets, a three-level delegation chain a reader had to trace to confirm reset coverage, and invariants held by discipline rather than construction. Committed whole and cleared whole, a half-set identity is unrepresentable: the fingerprint physically cannot exist without the model it identifies (the commit-time-claiming rule becomes structural), and the old compound `fingerprint == fp and activities` check collapsed to a field read. Deliberately **not** nested, so the exceptions are visible rather than buried in a uniform key list: `baseline_agg` (log-scoped — written by `commit_result` but surviving `clear_results`; inside the result object, the run-start clear would wipe it) and `experiment_error` (run-scoped display state, never a result field; named for slot symmetry with the as-discovered pair) — the two lifecycle asymmetries; the goals trio (interlocked with the widget-key generation machinery — bundling buys a name and risks the most delicate widget code); and widget-backed keys (Streamlit writes them top-level by construction). Rejected: a naming-only fix (the observed confusion came from reset *delegation*, which renames don't touch) and a separate `ui/session.py` home for `LogIdentity` (the commit contract lives in `discovery_manager`, its constructor's module — a types-only module would split one seam across two files).
- **`RunOutcome` discriminated union and `commit_result` helper** (`ui/services/run_manager.py`, `ui/interactive/execution_panel.py`): `RunState` previously mixed in-flight progress fields with terminal outcome fields (`result`, `error`, `cancelled`), forcing the execution panel to do a two-phase check: `current_run(ss)` (was a run started?) + `is_running(ss)` (is the thread still alive?). `RunOutcome` dataclass holds the terminal fields; `RunState.outcome: RunOutcome | None` starts as `None` (running) and is set atomically by the worker via a single attribute assignment (GIL-safe). `render_execution_panel` (the panel's current name — see below) checks `run_state.outcome is None` instead of `is_running(ss)` — one check replaces two, and the state machine is self-documenting. `commit_result(ss, result: ExperimentResult)` commits the result whole plus the log-scoped `baseline_agg` copy. It lives in `ui/services/run_manager.py` because it is the positive counterpart of `clear_results`, and that module already imports `ExperimentResult`. Snapshot discipline in the real-mode closure: only genuinely session-state-read values (`ss.log`'s model paths, and `experiment_dir` via its log name) are captured into locals before `def experiment_fn`; function parameters (`target`, `selected_resource_id`, `scenarios`, …) are already call-time-frozen locals, so the closure captures them directly — only genuinely session-state-read values need snapshot aliases.
- **N-goal selector with per-slot metric dropdowns** (`ui/interactive/goal_config.py`): a `st.radio` (1 … `len(MetricRegistry.rankable())`, default 1, `horizontal`, `label_visibility="collapsed"`) chooses how many goals are active — an explicit choice, not a derived count; the option list is derived from the registry so adding or removing a rankable metric self-adjusts the maximum (a hardcoded `[1, 2, 3]` would silently cap goals on grow and crash `available[0]` on shrink). Each active slot renders a metric `st.selectbox` (`key=f"goal_metric_{slot}"`, labelled via `per_case_display_name`) whose options are `MetricRegistry.rankable()` minus the metrics already chosen in earlier slots — uniqueness enforced by sequentially filtering against the running `chosen_metrics` list. A stale-key guard resets a slot whose stored metric was just claimed by an earlier slot, before the widget renders. There are **no cross-goal weights** — the aggregate score is the weakest-link `min` across goals (see the piecewise-linear scoring decision above), so there is no cross-goal weight widget or sum warning. (A metric with more than one selected indicator does get per-indicator weight inputs — a strictly intra-metric concept; see the indicator-model bullet above.) The count radio, metric pickers, and threshold inputs are one concern, so the selector lives in `goal_config.py` beside the editable thresholds (client request 2026-07) rather than in the sidebar. (A standalone goals-config module — a `ui/goals.py`-style `GOAL_METRICS` list — would be redundant with `MetricRegistry.rankable()`.)
- **Editable goal thresholds — persistence and validation** (`ui/interactive/goal_config.py`, `core/goals.py`, `app.py`): the goal breakpoints, previously silent ±10% derivations, are surfaced in Panel 3 as editable absolute-value Target/Worst inputs (baseline shown read-only between them — a fact, not a knob). Three mechanisms interlock: (1) **Persistence** — pure level-in-key would reset user edits on *every* re-run (the baseline moves by simulation noise, unlike `factor_levels`' deliberate context switches), and stable widget keys alone cannot persist either because Streamlit garbage-collects the state of unrendered widgets (the inputs unmount whenever no baseline is available: mid-first-run, after a baseline-failed run, or on a demo → real switch). Hence seed-in-key + durable `ss.goal_threshold_overrides`: the seed is the saved override when one exists (checked with `is not None` — an override of `0.0` is valid and a truthiness check would silently drop it) else `round(default, decimal_places)`; the key embeds the seed; an edit (`value != seed`) writes the override — untouched inputs track the moving baseline, edited inputs persist across re-runs and unmounts; a "Reset thresholds to defaults" button resets via `reset_goal_thresholds()` (`on_click`): it empties the dict **and bumps `ss.goal_threshold_reset_generation`, which is embedded in every threshold widget key**. Re-keying is the only reliable reset — the browser keeps a mounted widget's user-set value keyed by the widget's *identity* and re-sends it with the next rerun (`value=` is only the initial value on the client side too), so two prior attempts that left the identity unchanged were both undone one interaction later by the re-sent value, which the `value != seed` check re-wrote into overrides: (a) clearing the dict + explicit `st.rerun()`, and (b) an `on_click` callback deleting the `goal_target_*`/`goal_worst_*` widget-state keys server-side (AppTest cannot reproduce this failure — it has no frontend, so server-side deletion appears to work there). Observed symptom of both: Reset only worked when an intervening rerun had already moved the widget onto its override-seeded key. The same helper runs in `_clear_process_state()` (log reset / replacement), so no reset site leaves re-keyable client state behind. (2) **Validation** — `Goal.score()` silently produces a discontinuous cliff when `baseline_ref` lies outside `[target, worst]` (e.g. a 100→24.5 jump across an epsilon), so warn-and-score-anyway was rejected; dynamic `min/max` widget clamps anchored to the moving baseline were rejected because a persisted value outside refreshed bounds crashes `number_input` on render. Instead: static domain bounds only (`min_value=0`; `max_value=indicator.upper_bound` — 100 for the rework-rate percentage, `None` otherwise; computed default seeds are clamped to the bound, since a worst default of baseline × 1.1 can exceed 100 and would crash the widget), a per-indicator check `min(target, worst) <= baseline <= max(target, worst)` with a loud `st.error` naming the numbers, and the violating indicator dropping its whole metric goal from scoring while other goals still rank (Panel 5's score columns degrade by presence-filtering in `ui/table.py`). Validation, display, and `baseline_ref` all use the *rounded* baseline (`round(raw, decimal_places)`) — validating against the raw value would reject a worst pinned exactly at the displayed baseline with an error whose printed numbers look valid. (3) **Core guard** — `Goal.__post_init__` raises `ValueError` on the same violated ordering, making an unscorable Goal unconstructible (defense in depth behind the UI check, matching the `default_indicator` raise-at-the-boundary precedent). When `per_case_baseline` is `None` (real mode pre-first-run, or all baseline replications failed) only the metric pickers and indicator multiselects render, with a caption noting thresholds unlock once a run provides a baseline — goals are unconsumed in that state anyway (results and baseline arrive together), except the partial-failure case, which Panel 5's relocated baseline-failed `st.error` covers. `baseline_agg` deliberately **survives run start** (log-scoped — see `clear_results`): the previous run's baseline keeps seeding the threshold rows while a re-run is in flight, so the goals block no longer flip-flops between full rows (the frozen pre-click frame — fragment-scoped reruns leave the rest of the page as last painted) and collapsed pickers (any mid-run full rerun) within a single run.

- **Prompt cancellation in the real pipeline** (`core/simulation/executor.py`, `core/simulation/runner.py`): cancel now kills the in-flight Prosimos subprocesses instead of waiting out the longest running replication. `run_all` polls `stop_check` every `_STOP_POLL_SECONDS` (0.5s) via a timeout `wait` — not just per-completion, so a cancel is seen while every worker is mid-replication; on cancel a lock-guarded `_LiveProcesses` registry — populated by `runner.simulate`'s `on_spawn` callback (the executor's one worker-thread-written state) — `kill_all()`s the live `Popen`s **in parallel** (serial `taskkill`/`killpg` would add up across `os.cpu_count()` workers). `runner._run_logged` moved from `subprocess.run` to `Popen`+`wait` to expose the handle; `terminate_process` kills cross-platform (`taskkill /F /T` walks the Windows PID tree since `prosimos.exe` spawns a child `python.exe`; POSIX `killpg` SIGTERM→grace→SIGKILL, with `start_new_session` on kill-registered spawns + a self-group guard so it never signals the Streamlit server). `discover()` participates through the same hook (`discovery_manager`'s register callback). No partial-file cleanup is needed — on cancel `run_all` returns `False` and the orchestrator raises before any killed task reaches `_on_complete`, so no partial log is ever parsed; the files sit inert in gitignored `runs/`. **Value scales with the cases-per-replication run config** (user-controlled): neutral at 100–1000 cases (~1.5s, floored by the executor + UI 0.5s polls) but a major win at 10–50k cases, where cancel returns in 1–2s instead of hanging for minutes — verified end-to-end on Windows. The residual ~1.5s floor is the two 0.5s polls, not the kill. A remaining nicety: batching the Windows kills into one `taskkill /PID p1 /PID p2 …` call, if the parallel-thread kill ever shows overhead.

- **Model fidelity check + as-discovered runs** (`core/orchestrator.py`, `core/simulation/prosimos/replication_metrics.py`, `core/analysis.py`, `core/simulation/store.py`, `ui/services/run_manager.py`, `ui/interactive/fidelity_panel.py`; client requirements 2026-07): the **as-discovered run** simulates Simod's model exactly as discovered — untransformed, patternless — and the **model fidelity check** compares its replications against the same statistics computed from the uploaded log. **The vocabulary is load-bearing**: the as-discovered run is NOT the baseline (the *transformed* model at 0% automation — conflating them would silently reintroduce the distribution-shape confound the baseline redefinition removed), and new names use `fidelity`/`as_discovered`, never `baseline` or `validate`/`validation` (three existing meanings). Design decisions, each with its rejected twin: (1) **one orchestration home** — `run_as_discovered` lives beside `run_experiment` (same ingredients: executor, store paths, `replication_metrics`, the failure types); a feature-named `core/fidelity.py` was rejected as a second subprocess-orchestration home in a layer-named package, and the ~20-line comparison builder fails the new-module rule (`fidelity_table` mirrors `compare_to_baseline` in `analysis.py`). (2) **Fresh `store.new_experiment` dir per fidelity run**, model + params copied in; writing into the discovery dir was rejected — stale `rep_*` files would survive and contaminate `iter_replication_triples`' glob (the trust-checker walk and the exports). (3) **One cycle kernel, two callers, as a correctness precondition** — if the observed side re-implemented the per-case span, a drift would masquerade as model infidelity; sharing `cycle_stats` makes divergence unconstructible (this is why the kernel extraction shipped in the engine PR, not DRY aesthetics). (4) **`run_manager` minimally generalized** (`RunState.kind`) rather than mirrored — a `fidelity_manager` would be ~100 duplicated lines differing in key prefix (the `discovery_manager` mirror precedent is for *distinct* lifecycles, not identical ones); kind-less reuse was rejected because the two panels could not route. **Runs are mutually exclusive** — concurrent runs rejected: both species saturate `max_workers` subprocesses, and a second `start_experiment` would clobber `ss.run_state` under a live worker; each panel disables its Run button with a caption while the other kind is in flight. (5) **The fidelity toggle (default ON) pins cases-per-replication to the log's case count**: every compared statistic's sampling noise scales with n, so the per-replication spread — the noise yardstick of (6) — only measures the log's one-realization noise at equal n; the equal-n invariant lives in core (`run_as_discovered` raises `ValueError` before any file is written — the pinned widget is courtesy), and OFF is free exploration with no comparison. (6) **Model (std) is load-bearing, not decoration** (user-confirmed 2026-07): the log is one realization, so the per-replication std is the yardstick for whether Δ is systematic misfit or run-to-run noise; rendered "mean ± std" (NaN at one rep → em dash); a replication min–max band was the considered alternative. (7) **Comparison rows** are mean cycle + median cycle + rework rate — the tail-weighted average, the typical case, and the loop structure, three distinct facets of validity (client-agreed cull 2026-08). Excluded: cost (a log carries no calendars/rates — no observed ground truth); arrival-anchored spans (left truncation); case count as a row (≡ `--total_cases` by construction — a config echo, the rejected-bot-failure-rate precedent); min/max cycle (extreme order statistics — a parametric model cannot reproduce empirical extremes even when it fits, the calibration ladders showed them far off on otherwise-converged models, and they carry the table's highest replication variance, so their Δ generates false alarms; `prepare_replication_display` culls the same two columns for the same reason); and the cycle total (its Δ% equals the mean row's under pinned n by construction — a keep-for-familiarity row was considered and rejected against the does-it-inform bar). A p90 cycle row is the recorded alternative if tail fidelity is ever requested — an order statistic stable enough to compare, unlike the max (a new-indicator add: the ~4-file recipe plus an `ObservedStats` field). The XES caption is mandatory panel furniture: synthesized first starts (`start = end` for a case's first event) shorten the observed clock, so a small systematic positive Δ is expected for XES uploads. (8) **The observed side reads the Simod-ready converted CSV**, recomputed in the worker at run time (never a stale session snapshot); `discover()` returns it as the triple's third element so the UI never re-derives runner's naming rule, and the committed log's cheap case count feeds the pre-run caption. (9) **Its own top-level tab, not a panel** — the fidelity check ignores the target activity, factors, goals, and pattern entirely, so it is a distinct flow, not a pipeline stage; the page splits into Experiment / Model fidelity tabs sharing one sidebar. The rejected ladder: a *numbered panel* (would present an optional trust step as a required workflow stage — the numbers also appear across ~11 code files plus this document); an *in-page expander* (buries a full flow in a disclosure widget, and Streamlit expanders cannot nest — the shared failure surface's log-tail expander could not render inside one); *separate `st.navigation` pages* (Streamlit garbage-collects widget state of unrendered pages, so switching would reset the factor-level edits — the §6 trap class — and a run in flight commits only when its page's poller next renders). Tabs get the separation without either cost: every tab body runs on each rerun, hidden via CSS, so widget state and the 0.5s poller survive switches. `as_discovered_logs_zip` is separate from `event_logs_zip`, which would arcname under `baseline/` — a vocabulary violation in a downloaded artifact.

- **Calibrated discovery — the sidebar Discovery group** (`core/simulation/runner.py`, `ui/services/discovery_manager.py`, `ui/interactive/discovery_config.py`, `ui/interactive/discovery_panel.py`, `app.py`; client-resolved 2026-08 — the Apromore ~2% claim was confirmed to be metric-agreement, not simulated-vs-real fidelity): discovery quality is a user choice — Fast (`--one-shot`, minutes, scaling with log size — ~10 min on the 100k-event IssueTracker) vs Calibrated (Simod's optimization search fitting the model to the log, several times the Fast duration; measured on live experiments to take mean cycle Δ from +43% to −22% and median from +102% to +7% on a real-shaped log). Decisions, each with its rejected twin: (1) **the encoding is one value** — `discover(search_iterations: int | None)`, `None` = fast; a mode enum + budget pair was rejected because it makes the meaningless combination (fast, 7) representable, and Calibrated's identity IS its budget. (2) **The recipe lives in runner** as an f-string YAML (PyYAML rejected — not a dependency, and the stdlib-over-library precedent applies) written to `run_dir/simod_config.yaml` before the spawn — an inspectable artifact; every non-searched field is a deliberate pin (all five rationalized in `_calibrated_config`'s docstring — including the easy-to-"clean-up" empty `extraneous_activity_delays` mapping, which is the on-switch for that whole discovery stage); the three that carry cross-module weight: `clean_intermediate_files: true` upholds the exactly-one-BPMN invariant, `perform_final_evaluation: false` because the fidelity tab is the evaluation, fitted arrivals because observed-arrival replay measurably bought nothing and parametric arrivals are what the what-if experiments scale. (3) **Settings apply on the NEXT discovery** with a provenance-gated caption; **folding them into the discovery fingerprint was rejected as structurally broken**, not merely surprising: during a RUNNING discovery a widget flip would change the fingerprint, `discovery_phase` would return None, the RUNNING `st.stop()` would be skipped, and `needs_discovery` would fire `start_discovery` under the live Simod thread (the §6 concurrent-Simod class) while `_clear_process_state()` wiped results and thresholds as a radio side effect. A dedicated "Re-discover" button was also rejected — "Reset log" already is one-click re-discovery (the uploader retains its file, so `_clear_log` → rerun → `needs_discovery` auto-restarts with current widget values), and a button would create a third reset site against the two-helpers rule. (4) **The group renders above the phase routing** so it stays visible (frozen) during RUNNING and editable in the FAILED/CANCELLED banner state — "Retry discovery" picks up the current values because retry routes back through `needs_discovery`. Default mode Fast: an upload can never surprise the user with a multi-minute search; the intended workflow is fast look → fidelity tab → Calibrated + Reset log when the fit is poor.
